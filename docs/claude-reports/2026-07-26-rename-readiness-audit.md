## 2. Android package and iOS bundle id

| | Value | Where |
|---|---|---|
| Android package | `com.mrbarhum.sanadcare` | `app.json:21`, `google-services.json:12` |
| **iOS bundle id** | **NOT SET** | `app.json:10-12` is `"ios": { "icon": "./assets/expo.icon" }` — no `bundleIdentifier` |
| EAS project id | `64d5dd55-2fc6-4f15-805b-534a3444b410` | `app.json:51` |
| Firebase project | `sanad-care-4dbbc` | `google-services.json:4-5` |

**What changing the package actually costs:**
- **EAS project:** unaffected by the package change — EAS binds on `extra.eas.projectId`. But the **slug** is separately validated, so `app.json:4` and expo.dev must move together.
- **`google-services.json`: breaks immediately.** The file is keyed to `package_name`. You must register the new package as an Android app in the **same** Firebase project and re-download. Editing line 12 by hand does not work.
- **Every existing push token dies.** Expo push tokens are minted per (EAS `projectId` × installed app). A new package is a new app on the device. Devices only re-register when users install the renamed app *and* grant permission again. `sanad_device_id` also lives in SecureStore, which a fresh package install starts empty — so tokens register as new rows rather than updating old ones, and **the dead rows must be purged server-side** or `process-notification-outbox` keeps sending to them until receipts mark them invalid.
- **Google Play:** irreversible if published. See §0.
- **iOS:** nothing to break — the rename is the moment to **add** `ios.bundleIdentifier` for the first time. Note that iOS builds cannot be produced at all today without it.

## 3. The deep-link scheme

**Scheme: `sanadmobile`.** One scheme; no `https` universal links, no Android App Links, no `associatedDomains`, no custom `intentFilters`.

**Registration — 1 site:** `app.json:8`.

**Hardcoded in shipped code — 1 site (this is the Supabase redirect constant):**

  Consumed by `passwordResetRedirectTo()` → `src/app/(auth)/forgot-password.tsx` and `src/app/reset-password.tsx`. It is deliberately a literal, not `Linking.createURL`, because a dev client resolves that to an `exp+…` URL that would not match the Supabase allow-list.

**Comment-only — 4 sites, cosmetic:** `src/features/invitations/join-form.tsx:34` · `pending-join-link.tsx:16` · `pending-join.ts:6` · `pending-join.ts:60`.

**Derived automatically — need NO edit:**

- `src/features/invitations/pending-join.ts:62-81` — `joinCodeFromUrl()` matches on the `join-circle` path, any scheme.
- `src/app/reset-password.tsx` — `Linking.useLinkingURL()` / `getInitialURL()` are scheme-agnostic.

**Server-side counterpart (not in this repo):** the Supabase Auth **Redirect URLs** allow-list must gain `<newscheme>://reset-password` **before** the app ships, and must keep the old entry until every user has upgraded.

> **Milestone 7 note:** A1 moved password recovery to a 6-digit emailed code, which uses **no URL at all**. Once the Dashboard template drops `{{ .ConfirmationURL }}` and the in-flight emails expire, the scheme rename stops being able to break password recovery — its single highest-risk consequence. **Sequence the rename after A1 is live** and this item drops a whole risk tier.
