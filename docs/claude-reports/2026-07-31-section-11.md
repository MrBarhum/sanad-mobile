## The flagged bugs — every one fixed

The spec flagged five defects. All five are fixed, and the frames surfaced several more.

### 11a · `caregiver.today.logged` is a dead key
`grep` over `src/` returns 21 references to `caregiver.today.*` and **none** to `.logged`. A logged
dose renders its status pill, never a confirmation sentence, and no frame draws one. **Deleted from
both locales.**

### 11a · task meta rendered a raw ISO string
`due = task.due_time ? formatHm(...) : task.due_date` printed a bare `2026-07-28` to a caregiver
whenever a task had a date but no time. Added **`formatYmdShort`** to `utils/date.ts` — the same
contract as its neighbour `formatLongDate`, including the `ar-u-nu-latn` locale trick that keeps
Arabic on Western digits and the `try/catch` that falls back rather than blanking a row.

**Beyond the frame, flagged for sign-off:** the list deliberately carries work from *earlier* days
(`due_date <= today` in `useCaregiverToday`), and a task due three days ago rendered as a bare
«12:00» is indistinguishable from one due at noon today. An overdue task now leads with its day,
joined by the same «·» separator the dose rows already use. Same meta line, same tokens, honest
value — but the frame only ever draws a task due today, so this is an **addition** and is called out
as one. Only the *time* is LTR-isolated; isolating «28 يوليو» would force an LTR base direction onto
the month name.

### 11b · the mid-retry primary label
The branch keyed on `uploadFailed`, which `onRetryUpload` clears **before** the upload starts. React
Query flips `isPending` false on rejection in an earlier microtask than the `catch` that re-sets the
flag, so a render committed with `pending === false`, `uploadFailed === false` and a saved log — and
in that frame the sheet fell back to the dose-write branch: an **enabled «تسجيل الجرعة» over an
already-recorded dose**, photo field restored, «إلغاء» beneath. No frame draws that state.

It now branches on `photoOutstanding` (`savedLogId !== null && photo !== null`) — the fact, not the
error flag — so once the dose is saved the sheet can never present the dose write again.
`uploadFailed` keeps governing only the red alert, which is what it is for.

**That window was also a duplicate-record path**, which is why this is a bug and not a flicker.
`recordDose` chooses INSERT-vs-correct from `existingLogId`, taken from the dose **prop** — still
null after our own save — so a tap there would have written a **second `'given'` log for the same
dose**. For a caregiver that is a record implying a second dose given. `onSubmit` now returns early
into the retry when a log already exists, independently of the render fix.

### 11b · «إغلاق» forfeits the photo permanently
By the time that button is on screen the dose is saved, so the row renders a status pill instead of
the record button — **this sheet has no second entry point, and nothing else in the app can attach a
proof to an existing log.** One tap on a neutral «إغلاق» discarded a photo she deliberately took,
with no warning and no recovery.

The drawn label is unchanged; only the action is guarded, by the sanctioned lightweight
`confirmAction()` — an OS alert, so the section's *no nested confirms* rule for sheets still holds
(the same mechanism 11d's delete confirm uses). «إلغاء» before the dose is written keeps its bare
close: nothing is at stake there.

> **Both 11b defects are latent today.** `expo-image-picker` is absent from `package.json`, so
> `isDosePhotoCaptureAvailable()` is always false, `photo` is never set, and `uploadFailed` can never
> become true. They go live the moment that package is installed and an EAS build is cut — and
> nobody would re-audit this sheet at that moment.

### 11g · make-owner confirm omitted the auto-promotion
`transfer_circle_ownership` runs `update circle_members set role = 'admin'` for the new owner
(`20260610130200_lock_down_membership_and_ownership.sql`: *"The new owner … is promoted to admin"*).
The confirm read only «سيصبح {{name}} مالك الدائرة، وستفقد أنت صلاحيات المالك.» — so a
`remote_member` could be handed **full circle authority** by a manager who was never told the role
changed. **i18n value change only**, both locales; the RPC and every permission gate are untouched.
The second clause («يبقى دورك كما هو») was already accurate — the migration keeps the old owner's
admin role.

### 11g · save enabled with no change made
The role pane always opens with the member's current role selected, so its first frame showed an
armed «حفظ تغيير الدور» whose handler, on no change, quietly returned to the menu having saved
nothing. It is now `disabled` until something changes, and the no-op branch is **deleted** so the
handler can only ever mutate.

- Visible disabled state is a **local** `opacity: 0.45`, not a change to `Button`: the primitive
  deliberately exempts `primary` from the disabled fade app-wide (the "a primary CTA never greys
  out, it validates and explains" decision), and many primaries pass `disabled={pending}` alongside
  `loading`. Changing that guard would fade a spinner-bearing button on a dozen screens.
- **Behaviour note for the reviewer:** this removes today's escape hatch. A user who opened the role
  pane by mistake used to tap «حفظ» to get back; now «إلغاء» — right below, same 52dp — is the way
  out. That is correct, and it is a change on a live screen.

### 11g · no disclosure when promoting someone to caregiver
Inviting a caregiver mounts three plain-language cards (what she sees / what she does not / what is
never recorded) plus the mutual note. Changing an existing member's role to `caregiver` grants the
**identical RLS scope** and showed one sentence. A manager could hand out the whole scope by role
change having read a single line.

The disclosure is now `features/caregiver/caregiver-disclosure.tsx` and **both routes render it** —
an **extraction, not a fork**: the invite screen renders exactly what it rendered before, from the
new home (one-component-per-job holds). Gated on promotion **into** the role; leaving it needs only
the shell warning. **Zero new strings.**

### 11f · the broken 9×9 dots legend
Three coloured dots labelled «مسؤول» / «محرر» / «مشاهد» — three role names that appear on **no row**,
because rows read `circleMembers.roles.*` and say «مشرف» / «فرد من العائلة» / «عضو عن بُعد». A reader
could not map a single legend line to a single row. Worse, the bodies came from a **second copy** of
the role descriptions that had already drifted: the legend still described a «مشاهد» who «يمكنه
الاطلاع على المعلومات فقط» while the real tree had long since said «يتابع دائرة الرعاية عن بُعد.».
And with a caregiver present the manager dot and the caregiver dot were **the same green** — the key
was colour-only *and* ambiguous. (Milestone 8 recorded that last part and left it to the reskin.)

Replaced per the drawn fix: the legend now derives everything from the role itself — the glyph from
the same shared `roleVisual` the rows use (Crown / Edit3 / Eye / HandHelping), the label from
`circleMembers.roles.*`, the body from `circleMembers.roleDescriptions.*`. Legend and roster cannot
drift again, and the mark is a distinct **shape** rather than a tone, which is what the
never-colour-only law asks for. Seven orphaned `figma.members.legend.*` leaves deleted from both
locales; `caregiverDesc` survives on purpose as the deliberate **short** caregiver line.

### 11j · mixed numeral systems — **decision: Western digits**
The card showed «٦ أرقام» directly above the «000000» ghost placeholder and the «60» counter.
**Settled on Western digits throughout the `auth.*` namespace.** Reasons: (1) the Dar law already
mandates Western digits for every other numeric surface — times, dates, readings, invite codes;
(2) the placeholder and the counter on that very card were already Western; (3) `formatHm` and the
whole app render numerals that way. Six ar values changed; en was already Western, so parity was
untouched.

**Out of scope, still mixed (recommended follow-up):** `invitations.whatsappMessage` uses «١) ٢) ٣)»
as list markers beside a Western `{{code}}`, and `notifications.*.snooze*` says «٥ دقائق». Neither
is a Section-11 screen.

## Only a device can settle these

- **11j** — the centred code digits sit ~3dp left of true centre because RN counts the trailing
  `letterSpacing` in the measured width. A `paddingStart: 6` fixes it, but the effect cannot be
  confirmed anywhere but on hardware, so it was **not** shipped blind.
- **11b** — `confirmAction` fires an OS alert **from inside a `FigmaBottomSheet`**. No precedent for
  that in this codebase; verify on both platforms that the alert appears and that confirming actually
  closes the sheet. Also check the tightened 8dp action pair does not make a thumb aiming at
  «تسجيل الجرعة» clip «إلغاء».
- **11f** — whether the «واجهة مقدّم الرعاية» chip really wraps to its own meta line at 390dp and at
  large font scales; and whether the 14px Crown and HandHelping read apart in dark mode, where they
  share the `acc` tone and only the shape distinguishes them. That shape **is** the compensating
  control for the old colour-only key, so it must be seen, not assumed.

  local-part in a chip (`ibrahim.khalifeh91 (عضو سابق)`) may overflow, since `pickerChip` has no
  `flexShrink`.
- **11g** — the merged callout's internal rule is `1.5px` at `.35` opacity; sub-pixel hairlines can
  vanish or double on some Android densities. And confirm a *disabled* primary still reads as
  disabled at the local 0.45.
- **11a** — the record button's `line` border over the `btn` fill in **dark** is a genuinely
  low-contrast edge (what both the frame and the shipped `Button` draw); confirm it still reads as a
  button.
- **11d** — the `.45` disabled danger footer in dark is the least-contrast text in the block.

## How it was built

Two workflows. The first ran **ten read-only agents in parallel**, one per badge, each reading its
exact frame block, the spec entry, the shipped code, the Dar tokens and the Milestone 8/9 reports,
and returning a structured brief: an exhaustive frame transcription, a `file:line` account of the
current code, a delta table, the i18n set, and the flagged bugs with evidence. Implementation was
then done **screen by screen, sequentially, by hand**, with the quartet green and a conventional
commit after each. The second workflow ran five adversarial verifiers on distinct lenses —
behaviour preservation, project-law compliance, the no-caregiver promise, frame fidelity, and
shared-component blast radius.
